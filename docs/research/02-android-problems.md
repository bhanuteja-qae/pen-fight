# Godot 4.x → Android: Known Failure Modes for "Pen Fight"

Researched 2026-09-12. Project: Godot 4.x, GDScript, 2D RigidBody2D physics, turn-based hot-seat, touch flick input, CI-built signed AAB, Google Play target, no device build attempted yet.

Current context at time of writing: Godot stable is **4.7.x** (4.7.2, Aug 2026); Google Play's rolling target-API deadline is mid-transition (Android 16 / API 36 required for new apps from **Aug 31, 2026**, extendable to **Nov 1, 2026**). Anything version-specific below is flagged; unverifiable claims are marked **[UNVERIFIED]**.

## 1. Google Play policy/technical requirements that block or reject a build

| Requirement | Detail | Effect if missed | Source |
|---|---|---|---|
| Target API level | New apps/updates need **Android 16 (API 36)** from **Aug 31, 2026** (extension available to **Nov 1, 2026**). Existing published apps must already target **Android 15 (API 35)** or higher to stay visible to new users on newer-OS devices. | Play Console blocks upload/rejects the release; existing app can be hidden from new users on newer devices. | [Play Console Help – Target API level requirements](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en), [Median.co summary](https://median.co/blog/google-plays-target-api-level-requirement-for-android-apps) |
| 16 KB memory page size | Since **Nov 1, 2025**, new apps/updates targeting Android 15+ must ship native code (`.so`) that is 16 KB-page aligned. Devices with 16 KB pages (newer Android 15+ hardware) will not run misaligned native libraries. | Play Console **blocks the release** at upload if any `.so` is misaligned. | [Android Developers Blog, May 2025](https://android-developers.googleblog.com/2025/05/prepare-play-apps-for-devices-with-16kb-page-size.html), [Godot forum thread](https://forum.godotengine.org/t/google-console-16kb-memory-size-page-requirements-nov-1-2025-deadline/124764) |
| Godot's own compliance | 16 KB alignment landed in Godot via NDK bump to **r28.1.13356709**, merged for **Godot 4.5** (PR merged May 15, 2025, commit `82ea0b9`); back-ported to 3.6.2. **Godot 4.3 and 4.4 do NOT produce 16 KB-aligned `libgodot_android.so`** and will be rejected unless patched/rebuilt. Godot 4.6/4.7 inherit the fix. | Exporting from an old editor/template silently produces a build Play will reject at upload — not caught by the Godot exporter itself. | [PR #106358](https://github.com/godotengine/godot/pull/106358), [Issue #106313](https://github.com/godotengine/godot/issues/106313) |
| AAB-only | Google Play has required **Android App Bundle (.aab)** for all new app listings since **August 2021**; bare APKs are no longer accepted for new listings. In Godot's export preset, "Export Format" must be **Android App Bundle**, which also **forces "Use Custom Build" on**. | Upload rejected if you submit an APK for a new app. | [Ionic blog](https://ionic.io/blog/google-play-android-app-bundle-requirement-for-new-apps), [Android Developers – godot-export](https://developer.android.com/games/engines/godot/godot-export) |
| Play App Signing | Required to publish an AAB — you must enroll (upload your own key, or let Google generate one) before the first AAB upload; separates **upload key** from **app signing key**. | Cannot upload an AAB without enrolling first; losing the upload key later requires a Google support reset process. | [Play Console Help – Use Play App Signing](https://support.google.com/googleplay/android-developer/answer/9842756?hl=en) |
| Privacy policy + Data safety form | A privacy policy URL is mandatory to complete the **Data safety** section; the declared data collection/sharing must match what any SDK (ads, analytics, crash reporting) actually does. Since **April 10, 2025**, Android ID is explicitly classified as a device identifier that must be disclosed if any SDK reads it. | App rejected or suspended for a missing/incorrect Data safety form; SDK-caused non-disclosure is a common suspension cause. | [Play Console Help – Data safety](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en), [Google – data disclosure for AdMob](https://developers.google.com/admob/android/privacy/play-data-disclosure) |
| Ads SDK disclosure | If any monetization/ads SDK is later added (AdMob, mediation, etc.), each SDK's data collection must be individually reflected in the Data safety form — third-party SDK behavior counts as the app's own data collection. | Same as above — rejection/suspension. Currently N/A since project has no ads SDK yet, but flag for future. | [Google Admob – Play data disclosure](https://developers.google.com/admob/android/privacy/play-data-disclosure) |
| 64-bit native code | Play requires 64-bit support: if `armeabi-v7a` is included, `arm64-v8a` must also be included; if `x86` is included, `x86_64` must also be included. | Upload rejected for 32-bit-only native libraries. | [Android Developers – 64-bit support](https://developer.android.com/games/optimize/64-bit), [Android Developers – godot-export](https://developer.android.com/games/engines/godot/godot-export) |

**Not fully verified:** exact minimum `minSdkVersion` Play enforces (Play does not itself floor `minSdkVersion`, only `targetSdkVersion`) — **[UNVERIFIED, treat Godot's own default (21) as a starting point, not a Play requirement]**.

| Gradle `dexBuilderDebug` error when raising target SDK | Certain target SDK values interact badly with default Gradle/AGP versions bundled in older templates | Keep target SDK aligned with what the installed build-tools/AGP in the build template actually support; update the build template alongside SDK/AGP bumps. | [Issue #84253](https://github.com/godotengine/godot/issues/84253) |
| App crashes/won't install: Min SDK too high/low for device | Godot 4.2's Android template default was **minSdk 21 / targetSdk 33**; a device below `minSdk` can't install it, and Android 14+ has stricter behavior at low `minSdk` values. | Set `Min SDK` to a value covering your real user base (commonly 24–26 today) — don't leave stale defaults; verify against a real low-end test device. | [Godot forum – Choosing min/target SDK](https://forum.godotengine.org/t/choosing-min-and-target-sdks-used-to-compile-android-apk-file/25525) |
| Play upload rejected for missing arch | Only `armeabi-v7a` (or only `x86`) selected in export preset | Select **arm64-v8a** always; pair `armeabi-v7a`→also enable `arm64-v8a`, `x86`→also enable `x86_64`. ## 3. Runtime problems that don't show in the editor

| Symptom | Cause | Fix | Source |
|---|---|---|---|
| Black screen on launch (3D renders black, 2D fine) | Known Vulkan/Forward+/Mobile driver-compat issues on specific GPU/driver combos (Mali, Adreno) | Prefer the **Compatibility** (OpenGL ES 3) renderer, or **Mobile** renderer, for broad device support; project setting `rendering/renderer/rendering_method` (and `.mobile` override). Test on real hardware across GPU vendors — the editor's desktop GPU does not reproduce these bugs. Since this project is pure 2D RigidBody2D with no 3D, the well-documented **3D-specific black-screen bugs** are lower risk, but generic Vulkan-on-Android crashes on Mali have also been reported. | [Issue #73384](https://github.com/godotengine/godot/issues/73384), [Issue #82525](https://github.com/godotengine/godot/issues/82525), [Issue #115442 (Mali crash)](https://github.com/godotengine/godot/issues/115442), [How to choose a Godot renderer](https://knightli.com/en/2026/06/19/godot-renderer-forward-mobile-compatibility/) |
| App killed by system, reported as ANR | Android triggers ANR when the main/UI thread doesn't process input within ~5s (or doesn't draw); Godot issues include native synchronization blocking the main thread and heavy work in `Godot.getRotatedValues`-style native calls. | Never block the main thread with synchronous I/O or heavy loading — use threads (`Thread`, `WorkerThreadPool`) for asset loading, and avoid long synchronous scene loads; keep per-frame work bounded. Watch Play Console "Android vitals" ANR rate post-launch. | [Android Developers – ANRs](https://developer.android.com/topic/performance/vitals/anr), [Issue #99733](https://github.com/godotengine/godot/issues/99733), [Issue #75893](https://github.com/godotengine/godot/issues/75893) |
| Crash / broken rendering on resume (app switch, notification pull-down) | On Android, pausing the app destroys and recreates the EGL surface; Godot sets `setPreserveEGLContextOnPause(true)` but this is only a *hint*, not a guarantee — GPU-side resources can still be lost, and Godot does not reload them automatically in all cases. `NOTIFICATION_APPLICATION_PAUSED`/`_UNPAUSED` timing has had bugs (fired twice, or with `ProcessMode` interactions). | Handle `NOTIFICATION_APPLICATION_PAUSED` / `NOTIFICATION_APPLICATION_RESUMED` in your top-level script defensively (idempotent, no double-pause of game state); test app-switch and lock-screen resume repeatedly on real devices, not just the editor. | [Issue #22955 (context loss)](https://github.com/godotengine/godot/issues/22955), [PR #32064](https://github.com/godotengine/godot/pull/32064), [Issue #83160](https://github.com/godotengine/godot/issues/83160) |
| Game force-killed while briefly backgrounded (e.g. during an ad SDK popup) | Android's background process death / low-memory killer (`lmkd`) is more aggressive than desktop; Godot itself does not persist state across process death. | Design turn-based state to be serializable and periodically checkpoint (e.g., after each turn) to disk (`user://`) so a killed process can resume; don't assume the process survives any backgrounding. | [Issue #84069](https://github.com/godotengine/godot/issues/84069) — **partially anecdotal, treat root cause as [UNVERIFIED]** |
| Touch input feels "off": ghost mouse clicks, drag not firing, multi-touch not tracked | `emulate_mouse_from_touch` converts touch to synthetic mouse events, which can double-fire logic that also listens for `InputEventScreenTouch`/`InputEventScreenDrag`; there have also been Godot bugs where multitouch drag events failed to fire. | For a flick-based hot-seat game, handle **`InputEventScreenTouch`/`InputEventScreenDrag`** directly rather than relying on mouse emulation; if you don't need mouse compatibility, disable `input_devices/pointing/emulate_mouse_from_touch` in Project Settings to avoid duplicate event paths. Test two-finger/simultaneous touch explicitly since hot-seat play may have players' hands overlapping the screen. | [Issue #16651](https://github.com/godotengine/godot/issues/16651), [Godot forum – Screen touch/drag](https://forum.godotengine.org/t/inputeventscreentouch-and-inputeventscreendrag/58691) |
| UI/game elements pushed off-screen or under a notch | `DisplayServer.get_display_cutouts()` exists (Android-only) and returns cutout rects, but there is no automatic safe-area layout; `OS.get_window_safe_area()`'s value does not account for engine-side scaling, so raw values misalign with your UI coordinate space when using a stretch mode. There's also a **known stretch-mode regression on Android in Godot 4.5.2–4.6.2** pushing content off-screen. | Manually query `DisplayServer.get_display_cutouts()`/safe area and offset UI (e.g. via `MarginContainer`), converting through your `canvas_transform`/stretch scale factor; consider the community "Notchz" safe-area plugin. Pin your Godot version and re-test after any editor upgrade given the active regression. | [DisplayServer cutouts feature](https://github.com/godotengine/godot-proposals/issues/11106), [Issue #118153 (stretch-mode regression 4.5.2–4.6.2)](https://github.com/godotengine/godot/issues/118153), [Notchz plugin](https://godotengine.org/asset-library/asset/3926) |
| Wrong/locked orientation ignored on device despite editor preview being correct | Orientation set in `Project Settings → Display → Window → Handheld → Orientation`; older reports of `sensor_portrait` not working, and some builds ignoring the setting entirely (always landscape) on certain Godot versions. | Set explicit orientation appropriate to a physics-flick game (commonly `landscape` or `sensor_landscape` for a pen-fight-style game); test on-device since editor preview is not authoritative for this setting. | [Issue #55212](https://github.com/godotengine/godot/issues/55212), [Issue #10102](https://github.com/godotengine/godot/issues/10102) |
| Delayed/garbled audio SFX (flick "thwack" lands late) | AudioStreamPlayer has a reported >0.5s latency on Android in some device/driver combos, distinct from desktop; sample-rate mismatch between project mix rate and device forces real-time resampling, adding artifacts; default output latency (~15ms nominal, often ~23ms actual due to fixed 1024-frame buffer) plus underrun-prone buffer settings cause crackling. | Match project `audio/driver/mix_rate` to a common device rate (44100/48000); test actual perceived latency for flick-impact SFX on real hardware — don't rely on desktop timing. Treat as an ongoing, only partially fixed Godot issue. | [Issue #85442 (mobile audio delay)](https://github.com/godotengine/godot/issues/85442), [Godot forum – Audio latency Android](https://forum.godotengine.org/t/audio-latency-on-android-devices/134704) |

## 4. Mobile performance traps (2D, RigidBody2D-heavy hot-seat game)

| Trap | Detail | Mitigation | Source |
|---|---|---|---|
| Draw-call explosion in Compatibility/Mobile renderer | Each unique texture, unique material, or interruption of consecutive same-texture draws breaks 2D batching; too many small unbatched sprites tanks perf on mobile GPUs. | Atlas sprites into texture sheets; avoid a unique `ShaderMaterial` per sprite instance — apply post-processing shaders to one parent CanvasItem/backdrop rather than every child; keep the number of *distinct* textures per frame low. | [GLES2 2D batching article](https://godotengine.org/article/gles2-renderer-optimization-2d-batching/), [Sprite best practices](https://ilovesprites.com/blog/godot-sprite-nuances-best-practices) |
| 2D `Light2D`/shadows very expensive on Android | As few as ~5 dynamic 2D lights can visibly drop FPS; `Light2D` has been specifically reported "very slow on Android" vs desktop; shadow buffers add further cost even when static. | Avoid dynamic `Light2D`/2D shadows for this game unless essential; if used, keep count minimal, prefer baked/static lighting look via sprites, and test shadow buffer size on low-end Android hardware. | [Issue #9944 (Light2D slow on Android)](https://github.com/godotengine/godot/issues/9944), [Issue #4151](https://github.com/godotengine/godot/issues/4151) |
| MSAA cost / interactions with shadows | MSAA has non-trivial GPU cost on mobile tiled renderers; some Godot versions have shadow-rendering bugs specifically when MSAA is enabled. | For a 2D-only game, MSAA is generally unnecessary — leave `rendering/anti_aliasing/quality/msaa_2d` off or minimal; verify no shadow/MSAA interaction bug applies to your target Godot version before enabling. | [Issue #101831 (shadows break with MSAA)](https://github.com/godotengine/godot/issues/101831) — 3D-specific but indicates general fragility |
| Frequent `instantiate()` calls (e.g. spawning pens/trail particles/hit-effects each turn) | Runtime scene instancing does allocation + `_ready()`/node-setup overhead; on mobile this is more visible as frame hitches than on desktop. | Pool reusable nodes for anything spawned repeatedly (effects, projectiles) rather than instancing/freeing every turn; pre-warm pools during load, not during gameplay. | **[general Godot/gamedev best practice, not device-specific source found — treat as standard guidance rather than a cited claim]** |
| GDScript per-frame allocation (e.g. building arrays/dictionaries in `_process`/`_physics_process`) | Frequent temporary allocations in hot loops can cause visible stutter on mobile CPUs, more so than on desktop. | Avoid allocating new Arrays/Dictionaries/Strings inside `_process`/`_physics_process` every frame; reuse buffers; move heavy calc off the physics step where possible. | **[general guidance — not independently verified by a specific Godot mobile source in this research pass]** |
| Audio buffer underruns → crackling | Small/insufficient output buffer combined with GC-ish spikes or heavy frame work can starve the audio thread, especially with resampling due to mix-rate mismatch. | Keep `audio/driver/mix_rate` matched to device output; keep per-frame CPU spikes down (see above) so the audio thread isn't starved; test with device speaker, not just headphones/emulator. | [Godot forum – Audio latency Android](https://forum.godotengine.org/t/audio-latency-on-android/40339) |
| RigidBody2D behavior differs by device frame rate | Physics can be frame-rate dependent in subtle ways (time-scale interactions, jitter when render FPS drops below `physics_ticks_per_second`). For hot-seat local play this mostly affects *feel* rather than fairness (no netcode), but still risks inconsistent flick results across devices. | Keep gameplay logic in `_physics_process`, use a fixed `physics_ticks_per_second`, avoid relying on `Engine.time_scale` for game-affecting slow-mo, and if you increase `physics_ticks_per_second` also raise `physics/common/max_physics_steps_per_frame` to avoid slowdown perception on lower-end devices. | [Issue #48128 (RigidBody2D jitters on FPS drop)](https://github.com/godotengine/godot/issues/48128), [Godot forum – slower physics with slower FPS](https://forum.godotengine.org/t/slower-physics-movement-with-slower-fps/130685) |

## 6. Prioritized pre-first-build checklist

Ordered by how much pain each item prevents, given this project has never attempted an Android build.

1. **Pin exact Godot editor version and matching export templates.** Confirm the CI build agent and every dev machine use the *identical* Godot version (recommend current stable, e.g. 4.7.x, which includes the 16 KB page-size fix). Mismatched editor/template versions is the single most common first-export failure. *(Section 2)*
2. **Verify 16 KB page-size compliance before touching Play Console.** If using anything below Godot 4.5 (or an un-patched 4.3/4.4), the AAB will be rejected on upload from Nov 1, 2025 onward — this is a hard blocker discovered only at upload, not at export time. Confirm engine version now, not after CI is built. *(Section 1)*
3. **Install JDK 17 + correct Android SDK/cmdline-tools/NDK set and point Godot at them explicitly** (`build-tools;35.0.1`, `platforms;android-35`, `ndk;28.1.13356709` or current equivalents) — avoids the most common "cryptic Gradle failure" class of errors on the very first export. *(Section 2)*
4. **Decide the final `applicationId` (unique package name) now** — reverse-DNS, lowercase, no underscores/invalid segments — since it cannot change after first Play publish and a bad one fails silently at export, only failing at install/parse time. *(Section 2)*
5. **Set Export Format = Android App Bundle + Use Custom Build, and select arm64-v8a + armeabi-v7a architectures** so the CI-produced artifact is Play-upload-eligible on the first try (AAB-only, 64-bit requirement, Play App Signing enrollment done ahead of time). *(Sections 1–2)*
6. **Enable ETC2/ASTC VRAM compression in Project Settings before importing final art assets**, and delete `.godot/` cache if compression settings changed after assets were already imported — avoids a late, confusing re-import bug. *(Section 2)*
7. **Choose renderer deliberately (Compatibility or Mobile) rather than leaving default, and test on at least one real low/mid device per major GPU vendor (Mali, Adreno) before wide release** — black-screen and driver-specific Vulkan bugs are invisible in the editor and only surface on-device. *(Section 3)*
8. **Build touch input directly on `InputEventScreenTouch`/`InputEventScreenDrag`** for the flick mechanic rather than depending on `emulate_mouse_from_touch`, and explicitly test overlapping/near-simultaneous touches given hot-seat play. *(Sections 2–3)*
9. **Implement safe-area/cutout handling and lock orientation explicitly**, then verify on at least one notched device — layouts silently shifting or being pushed off-screen is a known live regression risk across Godot 4.5.2–4.6.2. *(Section 3)*
10. **Add defensive handling for `NOTIFICATION_APPLICATION_PAUSED`/resume and periodic game-state checkpointing to `user://`**, since Android can kill or resurface the app mid-turn (app switch, incoming call, low memory) and Godot does not persist state automatically. *(Section 3)*
11. **Prepare the Play Console privacy policy URL and Data safety form answers before first submission** — required even for a build with no ads/analytics yet, and must be revisited the moment any ad SDK is added. *(Section 1)*
12. **Only after the above: profile real hardware for 2D draw-call batching, avoid per-sprite unique materials, and keep `Light2D`/shadows minimal-to-absent** for this specific game, since it is a fast-feedback flick game where frame drops are directly felt as physics jank. *(Sections 3–4)*
13. **Set up `adb logcat godot:I *:S` + USB remote debug workflow now**, before the first real device test, so failures at steps 1–12 are diagnosable rather than mysterious. *(Section 5)*
